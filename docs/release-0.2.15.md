# 0.2.15 — 先选档，再花钱

## 为什么

0.2.14 把七档塞进了结果面板，而面板上的点击语义是"重跑"。于是第一次用某个档位，永远先花掉一次不想要的改写；"这一档到底叫什么"也得用一次模型调用去问。选和花必须是两个动作。

## 发生了什么

- **composer 里多了一个档位选择器**（星号按钮左边）：原生 `<select>` 胶囊，选项和设置页、面板档位条用的是同一批 `settings.mode.*` 文案，三处不会各叫各的名字。
- **选档只写状态，不发请求**（`ui-state` 的 `getPickedMode` / `pickMode`）。会话级、内存里，composer 卸载时清掉；没选过就回落到设置里的默认档，设置页仍是"默认值"的唯一来源。
- **真正发出去的是 `picked ?? settings.mode`**，快捷键触发也读同一个值。
- **面板档位条改成"只选中"**，重跑拆成独立按钮「用这一档重跑」，且只在选中的档位确实不同于上一跑时才出现。把七个名字读一遍不要钱，只有那个按钮要钱。
- **面板高亮表示"下一跑会用哪一档"**，不是"当前这份结果是哪一档写的" —— 因为选择器在结果出现之前就存在。
- 本地守卫拒绝（空/超长/相位忙）之后档位条仍然在：被拒绝的是那段草稿，不是选档这件事。

## 验证

- `tsc -p .` 干净；`vitest run`：38 文件 / 534 用例全过（新增 9 个）。
- `lib/index.js` 与 `lib/client.js` 已重建，`tests/preflight-built.mjs` 通过。

## 生效方式

宿主加载 `lib/`，**重启 DSH** 之后才会看到选择器和新的重跑按钮。
